# AskBI 系统设计文档

> 面向面试的"为什么"合集。每个决策都回答三个问题：是什么、为什么这样、不这样会怎样。

## 1. 业务定位与开源生态位

**场景**：对话式经营分析（ChatBI）。腾讯云 ChatBI、阿里瓴羊智能小Q（2025 年升级为 Agent 体系）、火山引擎 DataWind ChatBI 均为在售商业产品——这是被云厂商验证的付费市场，不是想象的需求。

**生态位**（诚实引用，不装原创）：

| 项目 | 思路 | 它没解决的（= 本项目主线） |
|---|---|---|
| Vanna | RAG 式 text2sql（问题-SQL 对 → 向量库） | 语义歧义场景弱、无质检闭环 |
| WrenAI | MDL 语义层 + 流水线 | 会话仅限 SQL 场景、无修订循环 |
| DB-GPT | 重型 AI 数据应用框架 | 输出质量无守护、上手成本高 |
| 腾讯云 ChatBI | NL2**DSL**2SQL 中间层（技术博客公开） | 商业闭源；本项目验证该路线的开源引擎级实现 |

多空辩论/对抗式多 Agent 等模式源自社区共识（TradingAgents 等），本项目借用其思想，聚焦工程化。

## 2. 确定性 / 不确定性分层决策表（核心设计哲学）

> 面试官原话级标准："哪些环节必须用 LLM 的模糊推理，哪些必须用硬编码锁死逻辑"。简单 if-else 能做却硬套大模型 = 为了用 AI 而用 AI。

| 环节 | 实现 | 为什么 |
|---|---|---|
| 预算路由（简单/复杂问题分流） | **纯代码规则**（关键词正则） | 一次廉价的规则就能省下整套多 Agent 开销；分类错了代价也可接受（多走完整图而已） |
| 歧义判定 | LLM | 歧义本身是语义问题，规则枚举不完 |
| 查询意图 → DSL | LLM（受白名单约束） | NL 的多样性必须模型兜；但输出被 pydantic 枚举校验，物理标识符由编译器渲染 |
| DSL → SQL | **纯代码编译器** | 指标表达式来自字典，杜绝模型写 SQL 的注入与幻觉面 |
| SQL 执行 | **纯代码沙箱** | 只读连接+守卫+超时，物理上不可写 |
| 归因计算（环比/维度分解） | **纯代码（SQL 聚合）** | "为什么下滑"的数字必须可复算；LLM 只解读不产数 |
| 叙述生成 | LLM | 讲人话是模型的事；但输入只有已计算的事实 |
| 数值核验 | **纯代码**（正则抽取+候选匹配） | 质检器本身不能依赖被检对象；确定性核验才能进 CI |
| 口径说明 | **字典直出** | 版本化、可审计 |
| 组装输出 | **纯代码** | 模板化工作没有不确定性 |

**一句话**：LLM 负责"理解与表达"，代码负责"计算与守护"，两者的边界写死在图结构里。

## 3. NL2DSL2SQL：为什么不直接 NL2SQL

1. **安全**：LLM 产出的 DSL 只含枚举字段（metric/dimension/filter 白名单），编译器渲染物理标识符——提示注入、幻觉表名在编译期不可达；值经过转义+取值校验。
2. **可控可解释**：DSL 是结构化意图，可以 diff、可以单测（编译器是纯函数）；直接生成的 SQL 是黑盒。
3. **口径统一**：所有指标表达式唯一来源是指标字典——"毛利率怎么算"永远一个答案，且带口径说明输出给用户。
4. **权限与治理的注入点**：行级权限、LIMIT 钳制、时间语义在编译期统一注入，LLM 无法绕过。

代价：DSL 表达力有边界（复杂 ad-hoc 查询覆盖不了）。取舍依据：经营分析 80% 的问题落在「指标×维度×过滤×时间」空间内；出界的明确拒答，好过编造。

## 4. 安全模型（四层纵深防御）

| 层 | 机制 | 测试锚点 |
|---|---|---|
| 连接层 | `duckdb.connect(read_only=True)`，物理不可写 | test_sandbox::test_readonly_is_physical |
| 语句层 | 单条 SELECT/WITH、危险词黑名单、多语句拒绝、掩码列拒绝 | test_sandbox 全组 |
| 编译层 | 字段/指标/维度全部白名单枚举；值转义；limit 钳制 ≤200 | test_compiler 全组 |
| 权限层 | 角色→区域作用域在编译期注入 WHERE（south 角色看不到华南外数据） | test_graph::test_row_level_permission |

**行级权限为什么在编译层而非 SQL 改写层**：改写任意 SQL 是出名的难题（子查询/CTE/别名都会绕过）；我们控制了 SQL 生成端，在源头注入最可靠。沙箱守卫做纵深防御兜底。

## 5. 失败降级矩阵

| 故障 | 行为 | 用户所见 |
|---|---|---|
| LLM 输出不合法 JSON/DSL 校验失败 | 带错误反馈重试 1 次；仍失败 → 拒答 | 明确的"无法转为合规查询" |
| SQL 执行报错 | 修复循环 ≤2 次（把错误信息回灌 sql_agent）；超限 → 拒答 | 带错误详情的拒答，非静默失败 |
| SQL 超时 | 独立连接 interrupt + wait_for | 拒答并说明超时 |
| 数据为空（权限外/无数据） | 规范化为空结果 + note | "空结果（可能为权限范围外）"而非 NULL 满屏 |
| 工具/语料缺失 | RAG 退化为空 few-shot；查询照常 | 无感 |
| QA 发现编造数字 | 打回 insight 重写（带整改反馈）≤2 轮；仍不过 → **带失败徽章输出**（降级而非吞掉） | 质检报告红色标记 |

原则：**宁可说"我不知道"，不编数字**。拒答是能力不是缺陷。

## 6. 预算路由与成本意识

- 问题含归因/趋势/对比语义 → 完整图（clarifier+sql+insight+qa，4 个 LLM 节点）
- 简单聚合 → 轻量链路（clarifier+sql，2 个 LLM 节点，跳过叙述与质检）
- 每节点 token 记账 → 任务库 → `/api/metrics` 看板；评测输出延迟 P50/P95 与 token 总量
- 回答"100 万用户先崩在哪"：DuckDB 单文件是分析型负载瓶颈 → 生产形态是查询下沉数仓/OLAP，DSL 编译器换 target 即可（这是 DSL 层的又一次回报）

## 8. 评测体系（可判对错是生命线）

四类样本：query（24 条，**执行结果与 gold SQL 逐行比对**，排序后 4 位小数精度）/ refusal（4）/ clarify（3）/ drill（2）。
消融开关：`--ablation sloppy`（模拟 LLM 编数字，验证 QA 闭环拦截率）、`--ablation no_qa`（关闭修订循环，度量质量损失）。

诚实声明：mock 模式下 100% 只证明**流水线与规则解析正确**；模型质量的真实数字必须用真实 provider 跑出（README 的表格记得替换）。sloppy 消融在 mock 下演示"编数字必被拦"，真实模型的数字错误率对比是同样的跑法。

## 9. 选型判断记录

| 决策 | 选择 | 备选与放弃原因 |
|---|---|---|
| 编排 | LangGraph | AutoGen（对话式编排，状态管理弱于显式图）；自研循环（重复造轮子，失去 checkpoint 生态） |
| OLTP/分析库 | DuckDB 单文件 | SQLite（分析聚合弱）；Postgres+pgvector（部署重，演示不友好）；生产替换成本已通过 DSL 层隔离 |
| RAG 后端 | TF-IDF 字符二元组（默认） | chroma 语义检索更强但要下载嵌入模型、引入非确定性——"够用的最简方案优先"，chroma 留了同接口后端 |
| LLM 接入 | OpenAI 兼容 SDK + provider 工厂 | 锁定任何一家都是负债；DeepSeek/GLM/Qwen 一个环境变量切换 |
| mock | 规则版 NL→DSL 解析器 | "假 LLM"让 CI 能跑端到端回归、评测先验证流水线再验证模型——mock 不是玩具，是测试基建 |
| SSE | 手写 StreamingResponse | sse-starlette 依赖少一个但格式就这么几行 |

## 10. 已知边界（面试主动交代比被问出来好）

1. DSL 表达力有限：窗口函数、复杂同比环比嵌套查询不支持——覆盖不了就拒答。
2. 澄清是"一次性"的：本实现返回澄清问题后结束回合，用户带答案重问；真正的 interrupt/human-in-the-loop 需要 checkpointer（改造点，知道怎么做）。
3. 单文件 DuckDB 的并发读：多副本只读连接可行，写路径（数据更新）需要离线重建——生产形态是数仓。
4. QA 的语义核验仍是 LLM：确定性部分（数字核验）可进 CI，语义部分是概率的——所以叫"闭环"不叫"保证"。
