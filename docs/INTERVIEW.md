# 面试深挖预演（AskBI）

> 用法：每题先自己答，再对照。答题时**结合项目里真实发生的事**（下面标注了代码位置），比背八股强一个量级。

## 架构与设计

**Q1 为什么用多 Agent，一个 Agent 串下来不行吗？**
一个循环式 Agent 理论上能做完，但有三个问题：(1) 职责边界模糊——澄清、查询、解读、质检混在一个 prompt 里，互相干扰且难测试；(2) 无法差异化重试——SQL 错了只需回 SQL 节点，不该重跑澄清；(3) 质检必须独立——自己检查自己的输出没有公信力。我的图里每个节点的存在都有理由：clarifier 处理语义歧义（规则枚举不完）、insight 把"已计算的事实"讲成人话、qa 是独立核验方。反过来说，router 我就没用 LLM——关键词规则够用且免费。**多 Agent 的价值不是角色多，是失败域隔离**。（`app/agents/graph.py`）

**Q2 为什么不直接 NL2SQL，要过一层 DSL？**
安全、可控、可测三点：LLM 输出只含白名单枚举字段，物理标识符由编译器渲染，提示注入在编译期不可达；DSL 是结构化意图，编译器是纯函数可以单测；指标口径、行级权限、LIMIT 策略在编译期统一注入，LLM 绕不过。代价是 DSL 表达力有边界，覆盖不了的问题我选择明确拒答。这个路线腾讯云 ChatBI 的技术博客也公开讲过（NL2DSL2SQL），我是拿开源栈验证它。（`app/data/dsl.py`）

**Q3 哪些环节用 LLM，哪些用代码？为什么？**
我有一张决策表（DESIGN.md 第 2 节）。判断标准：语义多样性问题（歧义判定、意图理解、把数字讲成人话）交给 LLM；计算、守护、模板化组装全部硬编码。一个例子：归因下钻的环比和维度贡献分解是 SQL 算的，LLM 拿到的 facts 里没有任何"需要它算"的东西——所以叙述里不可能出现算错的数字，只会出现"编的数字"，而编的会被 QA 抓住。

**Q4 系统给 100 万人用，先崩在哪里？**
分三层答：成本层——每个问题 2~4 个 LLM 调用，预算路由已经把简单查询压到 2 个，再往后是意图缓存（同问题直接回放任务库）；数据层——DuckDB 单文件扛不住并发，生产形态查询下沉数仓，我的 DSL 编译器把"生成端"和"执行端"隔离了，换 target 不动 Agent 层；质量层——评测集就是回归护栏，每次改 prompt 跑一遍。

## RAG / 检索

**Q5 你的 RAG 和 Vanna 有什么区别？**
Vanna 用问题-SQL 对的向量检索直接产 SQL；我的样例检索（问题→DSL 对）只是 sql_agent 的 few-shot 输入之一，最终输出还要过 pydantic 校验+取值校验+编译器。检索错了顶多变差，不会变得不安全。另外我的默认后端是 TF-IDF 字符二元组——中文短问句够用、零模型下载、完全确定，chroma 留了同接口可切换。**这是"够用的最简方案优先"的显式取舍**。（`app/rag/example_store.py`）

**Q6 检索不准怎么优化？**
先度量再优化：我的评测集能定位是检索的锅还是解析的锅。然后按序：扩充样例库（成功查询回流）、换语义后端（chroma）、query 改写。但优化前想清楚上限——样例只是 few-shot，主路径是 DSL 词表约束。

## 质检与幻觉

**Q7 幻觉怎么处理？——别只说 prompt 约束**
三层：源头（数字只能来自 SQL 结果集，LLM 不产数）、检测（QA 用正则抽叙述里的数字，和结果集/事实做带容差的候选匹配——百分比/千分位/正负号表达差异都归一化，日期豁免）、纠正（打回重写 ≤2 轮，仍不过带失败徽章降级输出）。容差设计踩过真实的坑：百分比域和原值域交叉匹配会造成漏报，我按 token 是否带 % 分域匹配解决的。（`app/agents/nodes.py` 的 check_numbers）

**Q8 QA 自己是 LLM，它错了怎么办？**
数值核验是纯代码，不依赖 LLM——这是它能进 CI 的原因。LLM 只补语义判断（叙述有没有夹带数据外的结论），它是概率的，所以整体叫"闭环"不叫"保证"。消融实验我做过：故意注入失真数字，确定性核验 2/2 拦截。

**Q9 用户问数据里没有的东西怎么办？**
明确拒答，三种情况三种路径：不是数据问题（写周报）→ clarifier 拒；指标不存在但很常见（客服满意度）→ clarifier 拒并说明"常见但未采集"；取值不存在（火星区域）→ 取值白名单校验拒。宁可说不知道，不编。拒答正确率在评测集里是独立指标。（拒答是能力不是缺陷——这句话面试可以直说）

## 安全

**Q10 SQL 注入怎么防？**
四层纵深：连接物理只读；语句守卫（单条 SELECT、危险词、多语句、掩码列）；编译层白名单+转义；值取值校验。测试里专门有注入用例：`华南' OR '1'='1` 被转义成无害的字符串条件。（`tests/test_sandbox.py`、`tests/test_compiler.py`）

**Q11 数据权限怎么设计？**
行级权限做在编译期：角色→区域作用域，编译时注入 WHERE。为什么不做 SQL 改写层——改写任意 SQL 是出名的难题，子查询/CTE 都能绕过；我控制了 SQL 生成端就从源头注入。前端可切角色演示：south 角色查东北，返回空结果+说明，而非报错。（`app/data/dsl.py` 的 ROLE_SCOPES）

## 工程与稳定性

**Q12 失败重试怎么做？**
两条回路：SQL 执行错误→带错误信息回灌 sql_agent 修复（≤2 次）；QA 不过→带整改反馈回 insight 重写（≤2 轮）。超限的行为是设计过的：降级输出（带失败徽章/明确拒答），不是吞异常。空结果也规范化了——聚合函数在空集上返回一行 NULL，我把它归一成"空结果+原因说明"，这是调试时真踩过的坑。

**Q13 成本怎么控制？**
预算路由（简单问题 2 个 LLM 节点，复杂 4 个）+ 每节点 token 记账 + `/api/metrics` 看板 + 评测输出 P95 延迟和 token 总量。路由用规则不用 LLM 的原因：省钱的方式不该先花钱。

**Q14 测试怎么组织的？**
76 项，五个层次：守卫单测（注入/危险词）、编译器单测（白名单/权限/钳制）、查询缓存与指代消解（E 系原创扩展）、图端到端（mock 查询/澄清/拒答/权限/QA 闭环，含故意编数字的消融自检）、API 测试（SSE 流/任务持久化）。关键设计：规则版 mock LLM 让端到端不依赖 API key——CI 永远绿，模型质量单独用评测集量。**mock 不是玩具，是测试基建**。

## 压力题

**Q15 这项目和 TradingAgents/DB-GPT 比创新在哪？**
诚实答：模式不新（多 Agent 编排、语义层、辩论都是社区共识），我的增量在工程化质量门——它们是研究框架形态（notebook/CLI、无产品化后端、无合规层、输出质量无守护），我补的是：可判对错的评测、确定性数值核验、拒答机制、行级权限、SSE 产品接口、MCP 服务化。这恰好是工程岗的职责范围。

**Q16 你最踩坑的一个 bug？**
讲 QA 数值核验的百分比域事故：叙述"下降 0.5%"（真实值 0.35%）没被拦住——因为毛利率原值恰好是 0.5006，跨数域匹配让编造的百分比撞上了真实的原值。修复是按 token 是否带 % 分域匹配+各自容差。这个故事说明质检器本身要被测试，我在测试里加了对应用例。（`tests/test_qa_check.py`）
