# AskBI 设计决策记录（ADR）

> 用途：这是我给项目里每个关键取舍写的决策底稿——面试被问"为什么不用 X"时，答案都在这里，
> 每条都能落到具体模块。格式：背景 → 决策 → 备选方案与放弃原因 → 后果与监控。

## ADR-1 为什么中间加一层 DSL，而不是直接 NL2SQL

- **背景**：业务问数最大的风险不是"生成不出来"，是"生成出来但错了"——注入、幻觉表名、口径漂移，三种错误都来自"让模型直接摸 SQL"。
- **决策**：LLM 只产出白名单约束的结构化意图（指标/维度/过滤全部枚举校验），SQL 由自研编译器统一渲染（dsl.py 的 compile_sql），行级权限与 LIMIT 钳制在编译期注入。
- **备选与放弃**：①直接 prompt 工程约束 NL2SQL——约束是"劝"，不是"防"，提示注入一戳就穿；②用语义层中间件（如 dbt 语义层）——重、且我们的指标字典只需要 8 类口径，杀鸡用牛刀；③Text2SQL 微调模型——算法向，且失去"口径可解释"。
- **后果与监控**：表达力受限（只能问字典内的指标）——这是有意的：问不了的问题走澄清/拒答而不是硬答。监控点：DSL 编译失败率、意图枚举越界率。
- **面试一句话**："我不是不信任模型的生成能力，是不把安全性寄托在生成上。"

## ADR-2 为什么选 DuckDB 当执行引擎

- **背景**：单机分析型查询、嵌入式部署、要只读沙箱。
- **决策**：DuckDB 只读连接 + guard 语句守卫 + 超时 interrupt + 结果钳制（sandbox.py）。
- **备选与放弃**：①SQLite——OLTP 出身，聚合分析慢；②Postgres——要起服务，个人项目部署重；③Pandas——把数据全载内存，10 万行以上就吃紧，且没有 SQL 的权限注入点。
- **后果与监控**：单写者限制（check_same_thread 处理过）——多租户时换 PG 或只读副本。监控点：查询超时次数、结果钳制触发次数。

## ADR-3 为什么 QA 核验用确定性代码而不用"再让 LLM 检查一遍"

- **背景**：叙述里的数字错了比答不出更糟（BI 场景数字就是结论）。
- **决策**：QA Agent 是确定性核验器：抽取叙述中所有数字 → 归一化表达（百分比/千分位/时长豁免）→ 与 SQL 结果集逐个比对 → 不符触发修订循环（nodes.py 的 check_numbers 链路）。
- **备选与放弃**：①"认真检查"提示词——不可验证、不可回归、不可归因；②再起一个 LLM 当 judge 复核——judge 自己会幻觉，且每次核验多一次调用；把"检查"做成代码才能进 CI。
- **后果与监控**：核验器有自己的误报模式（如把"近12个月"的 12 当业务数字）——已经用"坐标豁免"修掉，豁免规则本身也在评测集覆盖内。消融数字：关质检 93.9%→开 100%。
- **面试一句话**："LLM 检查 LLM 是用概率对抗概率；我用 SQL 结果对账，是对错分明的。"

## ADR-4 为什么做预算路由

- **背景**：评测 p95 114s 由归因题的审校修订循环主导，简单查询不需要全链路。
- **决策**：按意图分类走轻量/完整两条链路，简单查询 LLM 调用 4→2 次。
- **备选与放弃**：①全链路一律完整跑——延迟和成本都浪费在简单问题上；②所有查询砍链路——归因题的准确率会掉。
- **后果与监控**：分类器错判会让复杂问题走轻量链路——评测集按意图分层统计，轻量链路的失败率单独监控。

## ADR-5 为什么把指标查询封装成 MCP Server

- **背景**：问数能力如果只活在自家前端里，就只是个功能。
- **决策**：指标查询走 MCP stdio server 暴露（tools 原语），任何 MCP host 可复用。
- **备选与放弃**：①只留 REST API——生态封闭，外部 Agent 要自己写胶水；②HTTP MCP——stdio 够用且调试简单，HTTP 版列为扩展。
- **后果**：AB 从"产品"变成"生态组件"——这条在面试里是"功能 vs 平台思维"的差异化表达。
