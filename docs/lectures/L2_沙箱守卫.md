## 0. 防御模型总览

sandbox.py 模块 docstring（sandbox.py:1-7）把层次写得很清楚，对应到攻击者视角：

| 层 | 代码位置 | 防什么 |
|---|---|---|
| 1. 连接层：`read_only=True` | sandbox.py:101 | **物理层**：即使前面所有逻辑防御被绕过（例如将来有人手写 SQL 直连接口），写操作在文件系统层面就失败 |
| 2. 语句层：`guard()` | sandbox.py:51-68 | 多语句注入、非查询语句、危险关键词（COPY/ATTACH 导出侧信道）、引用掩码列 |
| 3. 编译层白名单 | dsl.py（见 L1） | 源头控制：LLM 只能产白名单 DSL，正常链路根本生成不了危险 SQL |
| 4. 资源层：LIMIT + 超时 interrupt | sandbox.py:66-67, 99-115 | DoS：无限行拖垮内存、笛卡尔积级别的重查询烧 CPU |

设计逻辑是**纵深防御（defense in depth）**：每层独立成立，假设上一层已经被突破。测试文件 `tests/test_sandbox.py` 对每一层都有锚点用例，这个"每层都有测试锚点"本身就是面试加分点（STUDY_GUIDE 4.3）。

## 1. `guard()` 逐行精读（sandbox.py:51-68）

```python
def guard(sql: str) -> str:
    s = sql.strip().rstrip(";").strip()          # ①
    if not s:
        raise SqlRejected("空语句")               # ②
    if ";" in s:
        raise SqlRejected("检测到多语句，已拒绝（仅允许单条查询）")   # ③
    if not re.match(r"^(select|with)\b", s, re.IGNORECASE):
        raise SqlRejected("仅允许 SELECT / WITH 查询")               # ④
    m = _FORBIDDEN.search(s)
    if m:
        raise SqlRejected(f"包含被禁止的关键词: {m.group(0)}")        # ⑤
    low = s.lower()
    for col in MASKED_FIELDS:
        if col in low:
            raise SqlRejected(f"引用了受限列: {col}")                  # ⑥
    if "limit" not in low:
        s += f"\nLIMIT {_MAX_ROWS}"              # ⑦
    return s
```

### ① 先剥掉结尾分号（sandbox.py:52）

`rstrip(";")` 让 `SELECT 1;` 规范成 `SELECT 1`。注意顺序：**先剥分号、再查内部分号**——这保证"合法的单条查询带尾分号"不被误杀，而真正的多语句（中间有 `;`）仍然会被 ③ 拦截。如果反过来先查 `;`，`SELECT 1;` 这种无害写法会被拒。

### ③ 拒绝多语句（sandbox.py:55-56）

防的是经典注入 `SELECT 1; DROP TABLE orders`（tests/test_sandbox.py:8-10）。duckdb 的 `con.execute` 对多语句的行为取决于驱动版本——**不依赖驱动语义，直接在语句层拒绝**，是更稳的选择：哪怕驱动只执行第一条，第二条进了日志/预解析也是污染源。

### ④ 白名单开头（sandbox.py:57-58）

只允许 `SELECT` / `WITH` 开头。`^(select|with)\b` 的 `\b` 很重要：防止 `SELECTIVE_x` 这类前缀混淆。注意这是**白名单而非黑名单**——黑名单永远列不全（`EXPLAIN`、`SUMMARIZE`、`DESCRIBE`…），白名单"不是查询就不要"语义清晰。

### ⑤ 危险关键词黑名单 `_FORBIDDEN`（sandbox.py:24-28）

```python
_FORBIDDEN = re.compile(
    r"\b(insert|update|delete|drop|alter|create|attach|detach|copy|export|import|"
    r"pragma|call|set|prepare|execute|vacuum|checkpoint)\b",
    re.IGNORECASE,
)
```

这一串不是随意罗列，按意图分组记忆：

- **写操作**：insert / update / delete / drop / alter / create——破坏数据；
- **文件与侧信道**：copy / export / import / attach / detach——DuckDB 的 `COPY orders TO 'x.csv'` 能把整库导出到任意路径（tests/test_sandbox.py:19 用了这条）；`ATTACH 'evil.db'` 能挂载外部库进而读写；
- **元编程/环境**：pragma / call / set / prepare / execute / vacuum / checkpoint——`PRAGMA database_list` 泄漏文件路径（tests/test_sandbox.py:19），`SET` 可改运行时配置，`PREPARE/EXECUTE` 可把语句拆开绕过开头白名单。

为什么 ④ 和 ⑤ 要同时存在？④ 拦"长得不像查询的"，⑤ 拦"披着查询外皮、内嵌危险子句的"——例如 `SELECT * FROM read_csv('/etc/passwd')` 以 SELECT 开头，能过 ④；若其中含 COPY 类函数名或受限列才会被 ⑥/⑤ 兜住。这是黑名单+白名单双轨的典型理由。

### ⑥ 掩码列拦截（sandbox.py:62-65）

```python
for col in MASKED_FIELDS:      # ("phone", "email", "id_card", "address", "password")  schema.py:36
    if col in low:
        raise SqlRejected(f"引用了受限列: {col}")
```

这里用的是**子串包含**而不是词边界——宁可误杀（列名 `telephone` 含 `phone` 也会被拒），不可漏杀。为什么这么狠？看 schema.py 的注释（schema.py:35-36）："MASKED_FIELDS 为纵深防御：即使有人手工构造 SQL 引用这些列，沙箱也会拒绝"。第一道防在数据模型层：customers 表**根本不含**手机号字段（最小暴露面，schema.py:3-5）；第二道才是这里。两道同时存在，因为列结构可能随仓库演进而变化，掩码表是独立于 schema 演进的静态承诺。

### ⑦ 强制 LIMIT（sandbox.py:66-67）

SQL 里没有 `LIMIT` 就补 `\nLIMIT 1000`（`_MAX_ROWS = 1000`，sandbox.py:29）。防"无聚合全表查询拖内存"。注意这只管"语句没写 limit"的情况——语句里写了 `LIMIT 10` 就尊重语句（编译层另有 200 上限，见 L1，两层互不冲突：编译器管 DSL 的 limit，guard 管裸 SQL 的 limit）。

## 2. 执行层：`Sandbox.execute` 与超时 interrupt（sandbox.py:99-115）

```python
async def execute(self, sql: str) -> QueryResult:
    safe_sql = guard(sql)
    con = duckdb.connect(self.db_path, read_only=True)   # 层1：物理只读
    try:
        return await asyncio.wait_for(
            asyncio.to_thread(self._run, con, safe_sql), timeout=self.timeout
        )
    except TimeoutError:
        # asyncio.to_thread 无法取消已开跑的线程，必须用 interrupt()
        # 从事件循环线程打断工作线程中的查询（duckdb 支持跨线程调用）
        con.interrupt()
        raise SqlTimeout(f"查询超过 {self.timeout}s 被中断") from None
    finally:
        try:
            con.close()
        except Exception:  # 极端竞态下 close 可能撞上未完全中止的查询
            pass
```

这段是全文件最值得讲透的并发细节：

1. **为什么要 to_thread**：duckdb 是同步驱动，直接在事件循环里 `execute` 会阻塞整个 FastAPI 进程；丢进线程池，事件循环可以继续服务 SSE 心跳等。
2. **为什么 wait_for 不够**：`asyncio.wait_for` 超时只能放弃**等待**，`asyncio.to_thread` 跑的是线程池里的同步函数——**线程无法被取消**，重查询会继续在后台烧 CPU。sandbox.py:107 的注释原话："asyncio.to_thread 无法取消已开跑的线程，必须用 interrupt()"。
3. **interrupt() 的机制**：duckdb 的 `con.interrupt()` 是线程安全的跨线程打断调用——从事件循环线程通知工作线程中止查询。测试 `tests/test_sandbox.py:50-61` 用 `CROSS JOIN`（约 1e10 行、优化器无法化简）证明超时真的会中断而不是空等。
4. **连接池毒化问题**：被打断的连接能不能复用？测试 `tests/test_sandbox.py:64-74`（`test_timeout_does_not_poison_pool`）验证：超时后**再查一次必须成功**。实现上靠 finally 里的 close——每次执行新建连接、用完即关，超时的连接被丢弃，生命周期无泄漏。
5. **`from None`**（sandbox.py:110）：抑制 TimeoutError 的异常链，让调用方拿到的 SqlTimeout 干净可读（wait_for 的 CancelledError 链在这里没有诊断价值）。
6. **close 也要 try/except**（sandbox.py:112-115）：interrupt 与 close 存在极端竞态——查询尚未完全中止时 close 会抛错，吞掉即可，不能让清理代码反过来污染结果。

### 结果规模控制（sandbox.py:85-97）

```python
rows = [[_jsonable(v) for v in row] for row in cur.fetchmany(_MAX_ROWS + 1)]
truncated = len(rows) > _MAX_ROWS
if truncated:
    rows = rows[:_MAX_ROWS]
```

`fetchmany(_MAX_ROWS + 1)` 是经典技巧：**多取一行**用于判断"后面还有没有数据"，从而产出准确的 `truncated` 标志（QueryResult.truncated，sandbox.py:45），最终呈现在答案的 `data_badge`（nodes.py:487）里告诉用户"数据已截断"。`_jsonable`（sandbox.py:71-76）把 date/datetime 转 ISO 字符串、Decimal 转 float——保证结果可以 JSON 序列化进 SSE/state。

### 同步版本 `execute_sync`（sandbox.py:119-135）

评测 runner 与脚本用（runner.py:46 判分时执行 gold SQL 就是它）。逻辑与异步版一致但没有线程包装——同步上下文里不需要。

## 4. 常见错误实现对比

| 错误写法 | 后果 | 正确做法（源码位置） |
|---|---|---|
| 只靠黑名单关键词、不做 SELECT 白名单开头 | `EXPLAIN`/`SUMMARIZE` 等漏网，且每加一个方言要补黑名单 | 白名单开头 + 黑名单双轨（sandbox.py:57-61） |
| `wait_for` 超时后不调 `interrupt()` 直接 close | 工作线程继续烧 CPU；close 撞上运行中查询抛错 | interrupt + 容错 close（sandbox.py:106-115） |
| 超时后复用同一个连接 | 中断的连接状态不可信，后续查询可能失败（池毒化） | 每次执行新建连接，finally close（sandbox.py:99-115） |
| `fetchall()` 全量取回 | 10 亿行结果直接 OOM，truncated 标志也做不准 | `fetchmany(_MAX_ROWS + 1)`（sandbox.py:89） |
| 掩码列用正则词边界匹配 | 大小写/嵌套引用变体可能漏；实现复杂 | 子串包含，宁误杀不漏杀（sandbox.py:62-65） |
| 把 guard 放在 LLM 输出信任链之后（先执行再校验） | 校验代码本身成为旁路 | execute 第一步就是 guard（sandbox.py:100），入口唯一 |

## 5. 面试讲法

**30 秒版**：
> SQL 执行前过四层防御：连接层 DuckDB 以 read_only 打开，物理上不可写；语句层 guard 拒绝多语句、只放行 SELECT/WITH 开头、黑名单拦 COPY/ATTACH 这类导出侧信道、掩码列子串匹配；编译层在 L1 讲过，源头就不生成危险 SQL；资源层强制 LIMIT 1000 加执行超时。超时有个细节：asyncio.to_thread 的线程不可取消，必须调 duckdb 的 interrupt() 跨线程打断，而且被打断的连接关掉后池不会毒化——这两个行为我都有测试锚点。

**3 分钟版**：
- 第一分钟：按"攻击者视角"走上面的攻击推演表，每一层举一条测试用例（tests/test_sandbox.py）。
- 第二分钟：讲 interrupt 并发细节（to_thread 不可取消 → interrupt() → close 竞态容错 → 池不毒化测试），展示"我知道这行代码为什么必须存在"。
- 第三分钟：讲取舍与局限：黑名单不可能完备（正黑名单是 SELECT/WITH 白名单兜底）；掩码列子串匹配会误杀但业务可接受；read_only 是最后的物理兜底——所以测试里专门有一条"绕过 guard 直接在只读连接上 CREATE TABLE 必须失败"（tests/test_sandbox.py:38-47），证明防御不依赖任何单点。

## 6. 自测五题（答案见文末折叠区）

1. `guard()` 为什么先 `rstrip(";")` 再检查内部 `;`？交换顺序会怎样？
2. `guard()` 已经保证只读查询了，连接层 `read_only=True` 是否多余？
3. `fetchmany(_MAX_ROWS + 1)` 为什么要多取一行？
4. 超时后 `con.close()` 为什么包在 try/except 里？如果不包会发生什么？
5. `_FORBIDDEN` 黑名单里有 `set` 和 `prepare`——它们看起来无害，为什么要禁？

<details>
<summary><strong>答案（先自己答再看）</strong></summary>

1. 剥尾分号是对"合法单条查询带分号"的兼容（用户/工具习惯），内部 `;` 才是多语句特征。若先查 `;`，`SELECT 1;` 会被误判为多语句拒绝——守卫的误杀率上升且毫无收益。源码顺序：sandbox.py:52 剥、55-56 查。
2. 不多余。guard 是**逻辑层**，保护的是"经过这个函数的 SQL"；而 read_only 是**物理层**，保护"任何经由该连接的任何操作"。假设将来新增代码路径忘了调 guard，或者依赖库内部发起辅助语句，物理只读仍然兜底。这正是 tests/test_sandbox.py:38-47 那条测试的立意：防御不能只有一层。
3. 如果只取 `_MAX_ROWS` 行，无法区分"恰好 1000 行"与"超过 1000 行被截断"。多取一行：取回 1001 行就说明截断了，置 `truncated=True` 并裁回 1000 行（sandbox.py:89-92），给前端的 data_badge 一个准确信号（nodes.py:487）。
4. interrupt 是异步通知，极端情况下 close 执行时查询尚未完全中止，duckdb 会抛错（sandbox.py:114 注释："极端竞态下 close 可能撞上未完全中止的查询"）。不包的话，清理路径的异常会覆盖掉本该抛出的 SqlTimeout，调用方看到的是莫名其妙的 close 错误——故障表现失真。
5. `SET` 可改 DuckDB 会话级配置（如内存限制、文件搜索路径），为后续语句的逃逸铺路；`PREPARE/EXECUTE` 能把任意语句先 PREPARE 再 EXECUTE——如果只做"开头必须是 SELECT"的检查，`PREPARE s FROM 'DROP ...'` + `EXECUTE s` 的组合能绕过开头白名单。黑名单把"元编程类"语句整体关掉，白名单检查才可靠。
</details>
