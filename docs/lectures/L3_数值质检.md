## 0. 问题定义

QA 节点要回答："叙述（narrative）里的数字，是不是都来自查询结果/计算事实？"

设计立场（nodes.py 模块注释 1-7 行、STUDY_GUIDE 4.5）：
- **确定性部分用代码**（`check_numbers`）：可复算、可进 CI、0 幻觉；
- **语义部分用 LLM**（`qa_node` 里的判断）：口径对不对、有没有夹带建议——这部分是概率的。

两者关系写在 qa_node 的判定行（nodes.py:441）：

```python
passed = (not det_issues) and bool(verdict.get("passed", True))
```

**确定性核验一票否决**：代码判定有问题，LLM 说没问题也没用。

## 1. 第一步：构建"允许值域"（nodes.py:371-382, 403-407）

```python
def _collect_numbers(value: Any, out: set[float]) -> None:
    if isinstance(value, bool):
        return
    if isinstance(value, (int, float)):
        out.add(round(float(value), 4))
        out.add(round(float(value), 2))
    elif isinstance(value, dict):
        for v in value.values():
            _collect_numbers(v, out)
    elif isinstance(value, (list, tuple)):
        for v in value:
            _collect_numbers(v, out)
```

三个细节：

1. **递归收集**：`facts`（归因事实，来自 `DrillDownFacts.as_context()`，analytics.py:29-41）是任意嵌套的 dict/list——维度分解里还有 `top_movers` 数组。递归是必须的。
2. **每个数存两个精度**：`round(v, 4)` 和 `round(v, 2)` 同时入集合（nodes.py:375-376）。为什么？结果集里存的是 `12345.67`，LLM 可能写 `12345.67` 也可能四舍五入写 `12345.7` 或 `12345.671`。多存两个舍入版本，配合后面的相对容差，把"合法的舍入表达"放进来。
3. **bool 先排除**：Python `bool` 是 `int` 子类，`True` 会被收成 1.0，而叙述里出现 1 应该匹配"真值 1"，不是布尔——先排除避免污染值域。

值域的三个来源（check_numbers 主体，nodes.py:403-407）：`result["rows"]`（查询结果表）、`facts`（归因事实）、`result["row_count"]`（行数本身也是叙述里合法的数字，如"共 8 行"）。

## 2. 第二步：从叙述抽数 + 豁免规则（nodes.py:364-368, 411-412）

三个正则：

```python
_NUM_RE = re.compile(r"(-?\d[\d,]*(?:\.\d+)?)\s*(%?)")            # nodes.py:364
# 日期（2026-09 / 2026年9月）与时长（近12个月 / 6个月）不参与数值核验：
# 它们是时间坐标/量词，不是业务数值
_DATE_RE = re.compile(r"\d{4}[-/年]\d{1,2}(?:[-/月]\d{1,2}日?)?")  # nodes.py:367
_DUR_RE  = re.compile(r"\d+(?:\.\d+)?\s*(?:个?月|年|天|日|小时|分钟|周|季度)")  # nodes.py:368
```

抽取流程（nodes.py:411-412）：

```python
clean = _DUR_RE.sub(" ", _DATE_RE.sub(" ", narrative))
for tok, pct in _NUM_RE.findall(clean):
    val = float(tok.replace(",", ""))
```

要点：
- **先剥日期和时长，再抽数字**，顺序不能反。注释给出了理由（nodes.py:365-366）："它们是时间坐标/量词，不是业务数值"。例："近12个月" 里的 12、"2026-09" 里的 2026 和 9——如果不豁免，叙述一开头就会误报。
- 这不是拍脑袋规则，是**破坏-修复实验修出来的**：STUDY_GUIDE 实验清单第 5 条就是"把 `_DUR_RE` 豁免删掉，观察『近12个月』数值误报复现"。
- `_NUM_RE` 的三个成分：`-?` 负号（变化率是负的）、`\d[\d,]*` 千分位（12,345）、`(\.(\.\d+)?)?\s*(%?)` 捕获百分号——**捕获组 2 是否为 `%` 决定了这个 token 进哪个匹配域**，这是全函数最关键的分岔。

## 3. 第三步：分域容差匹配 `_match_allowed`（nodes.py:385-398）

```python
def _match_allowed(val: float, allowed: set[float], is_pct: bool) -> bool:
    """数值匹配：带 % 的 token 只对百分比域，否则只对原值域，杜绝跨域误配。..."""
    floor = 0.061 if is_pct else 0.005
    for a in allowed:
        cands = (a * 100, -a * 100) if is_pct else (a, -a)
        for c in cands:
            if abs(val - c) <= max(floor, abs(c) * 0.011):
                return True
    return False
```

逐条拆：

### 3.1 分域（为什么这是踩坑修出来的）

带 `%` 的 token 只对"值×100"的候选集合比对（nodes.py:394 的 `cands = (a * 100, -a * 100) if is_pct else (a, -a)`）；不带 `%` 的 token 只对原值比对。**两个域永不互通**。

如果跨域会怎样（真实坑）：结果集里有毛利率 `0.0523`，叙述写"销售额高达 5.23%"——5.23 ≈ 0.0523×100，跨域匹配会把一个编造的百分比放过去；反过来更糟，叙述里编造的 `5.23`（无 %）会撞上真实的 `0.0523`。分域后，编造值必须**恰好**落在它声称的域里。docstring 的措辞是"杜绝跨域误配"（nodes.py:386）。

### 3.2 容差公式 `max(floor, |c| × 1.1%)`（nodes.py:392, 396）

两个成分各司其职：

- **floor（下限）**：百分比域 0.061，原值域 0.005。
  - 百分比 floor=0.061 放过什么：源值 `0.0523` 写成 `5.23%` 是精确的；但 LLM 可能写 `5.2%`（1 位小数舍入）→ |5.2 - 5.23| = 0.03 ≤ 0.061，放行。0.061 ≈ 0.05（半格）+ 一点余量，即"放过最后一位的四舍五入"。
  - 原值域 floor=0.005 放过什么：`12345.67` 写成 `12345.671`（4 位小数展开）差 0.001；写成千分位表达不改变数值。同时 0.005 很小——绝对值 8% 量级的篡改（docstring 例子：0.5006 → 0.5406，nodes.py:390）差 0.04，直接拦截。
- **相对项 `|c| × 0.011`（1.1%）**：大数场景下固定 floor 不够。销售额 `2,345,678.9` 被写成 `2,345,679`（合法的取整），差约 0.1 > 0.005——必须有随值放大的容差。1.1% 而不是 1%：舍入最多产生半个尾位（对 7 位有效数字约 0.5/10^6≈0.005%），1.1% 看似宽松，但它防的是"表达差异"，真正的编造通常是 8%+ 量级的自由发挥（SLOPPY 模拟的失真是 ×1.5 和 +8%，mock.py:276-277）。这个 1.1% 的取值 STUDY_GUIDE E2 验收标准里点名要求能解释。

### 3.3 `is_pct` 只由捕获组决定

`bool(pct)`（nodes.py:415 的调用处）——同一个数字 `5.23` 和 `5.23%` 是两个域的两次独立判断，绝不互相"借用"。

## 4. `check_numbers` 主函数（nodes.py:401-417）

```python
def check_numbers(narrative: str, result: dict, facts: dict) -> tuple[list[str], int]:
    """确定性核验：叙述中的每个数字必须能在结果集/事实中找到（含百分比换算）。"""
    allowed: set[float] = set()
    _collect_numbers(result.get("rows", []), allowed)
    _collect_numbers(facts, allowed)
    if result.get("row_count") is not None:
        _collect_numbers(result["row_count"], allowed)

    issues: list[str] = []
    checked = 0
    clean = _DUR_RE.sub(" ", _DATE_RE.sub(" ", narrative))
    for tok, pct in _NUM_RE.findall(clean):
        val = float(tok.replace(",", ""))
        checked += 1
        if not _match_allowed(val, allowed, bool(pct)):
            issues.append(f"叙述中的数字 {tok}{'%' if pct else ''} 未出现在查询结果或计算事实中（疑似编造）")
    return issues, checked
```

返回 `(issues, checked)`：issues 是给人看的整改反馈（会进 `revision_feedback`，nodes.py:457），checked 是核验总数（进 `qa_report.numbers_checked`，nodes.py:446，最终答案里能看到"核验了 N 个数字"）。测试 `tests/test_qa_check.py` 覆盖四类：真数字通过、编造数字拦截、百分比换算放行、千分位放行。

## 5. 修订循环：发现问题之后怎么办（qa_node + graph._after_qa）

`qa_node`（nodes.py:420-458）的流程：

1. 先跑 `check_numbers` 拿确定性 issues（nodes.py:421-423）；
2. LLM 做语义核验（一致/夹带结论/口径），prompt 里**把确定性 issues 一并喂给 LLM**（nodes.py:429-434）；
3. LLM 输出解析失败时兜底：`{"passed": not det_issues, "issues": det_issues}`（nodes.py:436-439）——代码结论直接生效，不因 LLM 失联而放行；
4. 未通过 → `revision_count += 1`，`revision_feedback = "; ".join(det_issues + llm_issues)`（nodes.py:455-457）。

循环与边界在图上（详见 L4）：`_after_qa`（graph.py:54-59）——未通过且未超限 → 回 `insight`（带着 feedback 重写叙述）；**超过 `max_qa_revisions`（config.py:40，默认 2）→ 直接 finalizer，带失败徽章降级出结果，不报错也不吞结果**（graph.py:57-58 注释："超限：带失败徽章出结果（降级而非报错）"）。

"整改反馈怎么用"在 insight 节点：`revision_feedback` 作为 payload 字段传给 LLM（nodes.py:312），并且 insight 的 system prompt 铁律（nodes.py:301-306）禁止 LLM 产出事实之外的任何数字——**从源头减少 check_numbers 要拦的东西**。质检是兜底，不是第一道防线。

消融实验的两个开关位置（L4 也会标）：
- `SLOPPY`：mock.py:266 的模块级布尔，`_insight` 里把变化率 ×1.5、当前值 +8%（mock.py:275-277）——模拟"LLM 自由心算/编造"，验证 QA 闭环拦截。测试 `tests/test_graph.py:46-56`（`test_sloppy_narrative_caught_by_qa`）断言 `qa.passed is False` 且 `revision_count >= 1`。
- `--ablation no_qa`：runner.py:66-67 把 `settings.max_qa_revisions` 临时设 0——修订循环直接关闭，量化"质检闭环值多少分"（93.9% → 100%，见 eval 报告）。

## 6. 常见错误实现对比

| 错误写法 | 后果 | 正确做法（源码位置） |
|---|---|---|
| 百分比 token 与原值混在一个集合比对 | 编造值 5.23 撞上真实 0.0523 放行（跨域误配） | 分域 `cands = (a*100, -a*100) if is_pct else (a, -a)`（nodes.py:394） |
| 只存原始精度一个值 | 合法舍入表达（12345.7）误报 | 同时入 `round(v,4)` 与 `round(v,2)`（nodes.py:375-376）+ 相对容差 |
| 固定绝对容差（如 0.01） | 大数取整（2345678.9→2345679）误报 | `max(floor, |c|×1.1%)` 相对容差（nodes.py:396） |
| 不豁免日期/时长 | "近12个月""2026-09" 全误报 | `_DATE_RE`/`_DUR_RE` 先剥（nodes.py:367-368, 411） |
| QA 失败后无限重试 | LLM 一直编 → 死循环烧钱 | `max_qa_revisions=2` + 超限降级（config.py:40、graph.py:57-58） |
| 只靠 LLM 自查"数字对不对" | 概率性，无法进 CI | 确定性核验一票否决（nodes.py:441） |

## 7. 面试讲法

**30 秒版**：
> 叙述里的每个数字都要能溯源。check_numbers 做三步：递归收集结果集和归因事实构建允许值域；用正则抽数前先剥掉日期和时长这两个豁免域——因为它们是时间坐标不是业务数值；然后分域容差匹配——带百分号的 token 只对"值×100"域比对，绝对不跨域，容差取 max(0.061, 1.1%)，放过舍入表达、拦住 8% 量级的篡改。这里分域是被真实坑修出来的：不分域的话编造的 5.23 会撞上真实的 0.0523。整个函数是纯函数，能进 CI。

**3 分钟版**：
- 第一分钟：三步流程 + 允许值域为什么含 row_count、为什么每数存两个精度。
- 第二分钟：讲坑。百分比跨域误配的因果链：结果集有 0.0523 → 叙述编了"5.23%" → 早期版本跨域匹配放行 → 修成 is_pct 分域。再讲第二个坑：删掉 _DUR_RE 豁免后"近12个月"误报（破坏-修复实验 5）。
- 第三分钟：讲闭环。QA 失败 → revision_feedback 打回 insight → 超过 max_qa_revisions=2 带失败徽章降级而不是死循环；消融实验用 SLOPPY 注入编数字验证拦截（93.9%→100% 的差距就是这套闭环的价值）。收尾强调：insight 的 prompt 铁律"禁止自己算新数字"是源头治理，check_numbers 是确定性兜底——两层设计互为犄角。

## 8. 自测五题（答案见文末折叠区）

1. 为什么 `_collect_numbers` 对每个数字同时存 `round(v,4)` 和 `round(v,2)` 两个版本？
2. 容差公式里 `floor=0.061`（百分比域）和 `0.005`（原值域）分别放过什么、拦住什么？
3. 叙述"近 12 个月合计 1,234,567 元，同比 2026-09 上升 5.2%"——哪些 token 会被抽出来核验？哪些被豁免？
4. `qa_node` 里 LLM 输出解析失败时为什么兜底为 `passed = not det_issues` 而不是 `passed = True`？
5. SLOPPY 开关改的是哪个函数的什么行为？为什么把"编数字"模拟放在 insight 层而不是 qa 层？

<details>
<summary><strong>答案（先自己答再看）</strong></summary>

1. 结果集浮点存的是全精度（如 12345.67），LLM 叙述里可能写 4 位小数展开（12345.6701）也可能 2 位以内舍入（12345.67 / 12345.7）。两个舍入版本 + `_match_allowed` 的相对容差，把"合法的精度表达"全放进白名单，同时不影响对量级篡改的拦截（nodes.py:375-376）。
2. 百分比 floor 0.061 放过 1 位小数舍入（0.3%↔0.35% 这类，docstring 原话 nodes.py:388）；原值域 floor 0.005 放过千分位/4 位小数表达，同时拦得住 0.5006→0.5406 这种 8% 量级篡改（docstring 原话 nodes.py:389-390）。floor 处理"小数的表达差异"，相对项 `|c|×1.1%` 处理"大数的舍入差异"——两者取 max（nodes.py:396）。
3. 豁免："近 12 个月"（`_DUR_RE`）、"2026-09"（`_DATE_RE`）。被抽核验：`1,234,567`（千分位剥离后比对原值域）、`5.2`+`%`（进百分比域，与结果中 0.052 或 0.0523×100 比对，|5.2-5.23|=0.03≤0.061 放行——前提是真实变化率确实是 0.052 左右）。
4. `passed = not det_issues`（nodes.py:439）意味着：LLM 失联时，确定性核验的结论仍然生效——有问题就不过，没问题才放行（此时语义核验缺席，相当于只跑确定性部分）。若兜底 True，攻击面变成"把 LLM 输出搞成解析失败即可绕过语义核验"。
5. `SLOPPY` 是 mock.py:266 的模块级开关，`_insight`（mock.py:275-277）在生成叙述时把变化率 ×1.5、当前值 +8%——模拟 LLM 编造/心算。放在 insight 层因为编数字的责任主体就是"写叙述"的那一方（真实 LLM 的失败模式在生成端）；qa 层保持诚实，才能测出"qa 能不能拦住 insight 的错"——这正是闭环要验证的方向（mock 恒过的 `_qa`，mock.py:297-299，也保证了拦截功劳全归确定性核验+回路）。
</details>
