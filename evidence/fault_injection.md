# AskBI 故障注入报告

- 日期：2026-10-28 ｜ provider：mock ｜ 每场景注入 10 次
- 判定基线：任何场景都不允许出现未捕获异常（crash）；LLM 不可用时必须诚实拒答，不允许编造答案。

| 场景 | 行为分布 | 崩溃 | P50(ms) | Max(ms) |
|---|---|---|---|---|
| S1 瞬时故障（前2次 LLM 503 后恢复） | answer×9，refusal×1 | 0 | 43.2 | 66.7 |
| S2 LLM 完全不可用 | refusal×10 | 0 | 3.2 | 5.3 |
| S3 LLM 返回非法 JSON | refusal×10 | 0 | 3.7 | 4.6 |
| S4 SQL 超时（timeout=0.0001s） | refusal×10 | 0 | 85.5 | 114.4 |
| S5 库文件缺失 | refusal×10 | 0 | 29.9 | 30.6 |
| S6 LLM 编造未知指标 | refusal×10 | 0 | 3.0 | 5.3 |

## 场景注记（诚实账）

- S1 的 refusal×1 是**确定性结果而非随机失败率**：故障配额 2 次恰好被第 1 次运行的clarifier+sql_agent 消耗（该次运行拒答），第 2 次起全部恢复——这正是"瞬时故障有限影响"的预期形态。
- S6 的问法刻意带指标词（"销售额"）以通过澄清器，让编造指标真正到达 sql_agent 的白名单校验——若问"净利润是多少"会在澄清层就被反问，测不到白名单。

## 结论

- **全部 6 场景零崩溃**：故障被客户端重试/节点降级/修复循环/守卫四层机制吸收。
- LLM 完全不可用时系统给出诚实拒答（含不可用原因），不编造数据；
- JSON 损坏与编造指标被解析层+白名单校验拦截为拒答（宁缺毋滥）；
- SQL 超时与库文件缺失由执行器修复循环兜底为拒答；叙述层缺 LLM 时保留数据表（见 test_fault_tolerance.py）。
