# AskBI 压测报告（HTTP 全栈双口径：进程内 vs uvicorn 真进程，2026-11-05 同机同日）

- **口径**：服务端 = PROFILE=conservative + LLM_PROVIDER=mock + uvicorn 单进程单 worker；客户端 = httpx 异步 SSE 逐行解析（消费到 final 帧为止的端到端延迟）；问题配比 light:heavy≈2:1 与进程内 load_test.py 完全一致；每点位预热 5 请求不计入。
- **方法论**（沿用 agentgate 压测三教训）：①附加开销在 c=1 无排队测；②同客户端打 /api/health（零业务地板）检验客户端瓶颈，逼近地板的数字如实标注；③组件分解——LLM 串行调用次数×单次延迟是结构性瓶颈，HTTP 是常数项附加。
- **环境**：Windows / Python 3.12.4 / uvicorn 0.54.0 / httpx 0.28.1。

## 表1 · c=1 附加开销分解（delay=0，缓存关，20 请求）

| 口径 | P50(ms) | P95(ms) | 说明 |
|---|---|---|---|
| 进程内 run_ask 直调 | 49.4 | 375.8 | 编排+SQL 本体（无 HTTP） |
| HTTP 全栈（SSE 全链） | 54.5 | 355.1 | +uvicorn+FastAPI+SSE 分帧+JSON+客户端解析 |
| GET /api/health 地板 | 3.9 | — | 客户端+框架零业务地板 |

**每请求 HTTP 全栈附加开销 ≈ 5.1ms**（c=1 P50 差值法：HTTP 全栈 54.5ms − 进程内 49.4ms）。其中 3.9ms 是任意 HTTP 请求都要付的客户端+框架地板，SSE 多帧会话（约 10 帧）的净附加 ≈ 1.2ms——附加开销占比随 LLM 延迟上升而稀释（delay=300ms 时约 0.4%）。

## 归因结论

- **客户端瓶颈检验**：c=50 /api/health 地板 QPS = 579.8（单发小响应负载），/api/ask（delay=0）QPS = 56.2——未逼近地板，客户端不是瓶颈。注意 health 是单发小响应负载，SSE 流式会话的客户端成本更高，但 c=1 分解已证明 SSE 净附加仅 ~1.2ms——客户端解析开销可控。
- **delay=0 高并发 0.53× 的归因（诚实标注共址伪影）**：客户端与 uvicorn 同机共址、争抢同核 CPU——SSE 逐行解析与 FastAPI 序列化在同一颗 CPU 上排队，**共址客户端的 delay=0 高并发数字不能当服务端容量上限**；health c=50 P50 76.57ms vs c=1 3.9ms 也印证高并发下排队主导延迟。
- **瓶颈归属不变（delay=300ms = 真实形态近似）**：HTTP/进程内 = 0.92~0.97×，框架附加被 LLM 等待摊薄；P50 ≈ 4×300ms 证实结构性瓶颈 = LLM 串行调用次数 × 单次延迟（light 2 次/full 4 次）——吞吐天花板在 LLM 供应商侧，单机编排远未到需要拆服务/消息队列的规模。
- **缓存收益随瓶颈位置变化**：c=1 +36.4%（P50 14.0ms vs 54.5ms，重复查询整链短路）；高并发 +3~4%（瓶颈移到共址 CPU，SQL+LLM 占比下降）；10-28 进程内存档 +12% 为中间形态（evidence/load_test.md）。上线盯 stats().hit_rate，低于 20% 就关掉。
- **同日复测 vs 10-28 存档矩阵**：进程内口径在 ±4% 噪声内复现（c=50 delay=0 106.9 vs 存档 110.8、delay=300 41.5 vs 存档 43.2）——双口径可复现，存档矩阵仍有效。
- 错误率：全程 mock 确定性，0 错误（异常即计入 errors 列）。
